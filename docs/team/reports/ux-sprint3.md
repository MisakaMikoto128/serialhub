- 测试人: 体验官 (UX 角色), 2026-09-12 · 背景: dev-sprint3.md (含 ADR-9/10) / qa-sprint3.md 已读, 黑盒用户姿态
- 环境: Windows 11 · 2560×1600 物理 · 150% 缩放 · `target/release/serialhub.exe`
- 主流程: 无 `--port` 冷启动 (closed 态) → **纯 UI 配置** COM2/115200/8N2/xonxoff/max-clients=3 → 打开收发 →
  复制页面等价命令 → 杀掉 UI 实例 → **原样重跑复制来的命令** 验证对等; 反向 CLI `--flow xonxoff

  组合框选项与数字输入全部生效经截图+API 双确认

## 总评

**"同一件事 UI 做一遍、CLI 做一遍"的骨架是真的立住了 —— 等价命令、对照表、max-clients/addr 双落点全部到位, 自我重启断档 ≈0 秒、配置全保留; 但对等性恰在 flow 上单向破缺: CLI 设的 flow UI 看不见、等价命令会丢掉、UI 重开会把它静默抹掉, 叠加自重启后发送区永久卡死, 这两条 P1 修掉之前,"面向全体开发者"的承诺只能算兑现了一半。**

## 反馈清单

### P0 阻塞

无。主流程全部走得通, 无崩溃/残留。

### P1 难受

**P1-1 等价命令与剪贴板漏掉 `--flow`, 复制即失真**
- 现象: 表单 流控=XON/XOFF 时, 「等价 CLI 命令」与 📋 复制进剪贴板的内容均为
  `serialhub --port COM2 --baud 115200 --config 8N2 --max-clients 3 --addr 127.0.0.1:8080`
  —— 没有 `--flow xonxoff` (ux-sprint3/02-ui-configured.png、98-panel-closeup.png; 剪贴板实测逐字核对)。
- 为什么难受: FR-9c 承诺"与当前控制台配置**完全等价**", 而用户照抄命令起出的实例 flow=none ——
  对等性承诺在 flow 上第一次破缺; 且复制动作本身是这一功能的全部意义。
- 建议: 等价命令渲染取值加入 flow (含 none 时可省略, 非 none 必须带上)。

**P1-2 CLI 设的 flow 在 UI 零回显, 且 UI 重开会把它静默抹掉**
- 现象: ① `--flow xonxoff --max-clients 2` CLI 起实例, UI 流控下拉显示「无」而 最大客户端=2 正确回显
  (ux-sprint3/04-cli-echo-panel.png) —— 因为 status 10 字段没有 flow, UI 无从得知; ② 更危险的行为级
  实锤: 此时用户在 UI 上关→开 (最普通的操作), 探针实测桥的 flow 已变 none —— 对端发的
  `\x13\x11FLOWPROBE` 以**裸数据**形式穿过桥送达 WS (flow=none 特征), 而非被驱动消费 —— 流控被
  静默降级, 无任何提示。
- 为什么难受: FR-9 要消灭的"不对等"恰好在这里复活: CLI→UI 不可见, UI→CLI 会抹掉。用户在 UI 上
  任何一次开关串口, 都可能悄悄丢掉流控配置, 排查方向都会被带偏。
- 建议: status 增加 flow 字段 (或提供 GET /api/config), UI 表单用真实值初始化; 短期兜底: flow≠none
  时等价命令块加一行警示。

**P1-3 自我重启后发送区永久禁用, 关→开 与 F5 都救不回来**
- 现象: 「应用并重启」→「确认重启?」两段确认后, 新窗口: 徽章「已打开」+「WS 已连接」, 但发送输入框与
  发送按钮禁用, 提示"串口未打开, 发送区禁用" (ux-sprint3/06-restarted-window.png、07-sendarea-after-restart.png);
  UIA 实测 发送输入/按钮 IsEnabled=False; 用户自救路径 关→开 **无效**, F5 **无效**; RX 正常 (对端发 23B,
  rxBytes 0→23)。对照: 同为 `--port COM1` 的冷启动实例 (sprint 2/3 均测) 发送区正常 → 重启路径特有。
- 为什么难受: 自重启是 FR-9a 的招牌功能, 结果换来的控制台"半身不遂" —— 收得了数据发不出指令,
  只能再重启整个进程; 且提示文案 (串口未打开) 与事实 (已打开) 自相矛盾, 把用户往错误方向引。
- 建议: 排查页面加载即 phase=open 时发送区使能状态的初始化路径 (疑似只监听 closed→open 跳变,
  页面加载时已 open 则无跳变); 提示文案按真实原因区分 (未打开 / WS 未连接)。

### P2 锦上添花

**P2-1 拒连原因不透传, 被拒的开发者两眼一抹黑** (走查 4)
- 现象: max-clients=1 后, 第二个 WS 客户端被 Close(1013, "max clients") —— 脚本作者能看到 code/reason
  (websockets 异常逐字段可读, 这半边合格); 但**浏览器页**作为被拒方: 徽章「WS 未连接」+ 控制台
  **零条消息** (ux-sprint3/08-browser-rejected-1440.png), 页面不解释、不提示, 只有开 DevTools 查 WS 帧
  才能发现 1013。且该页发送区提示仍是"串口未打开, 发送区禁用" —— 真实原因是 WS 被拒, 文案误导。
- 建议: 页面捕获 close code/reason, 徽章旁给一行「连接被拒: 已达最大客户端数 (1013)」; 发送区禁用
  提示按真实原因分档 (串口未打开 / WS 未连接或被拒)。

**P2-2 浏览器页的「退出程序」可点但无效**
- 现象: 壳标记门控已生效 (浏览器页点击后壳进程无恙, ux-sprint3/10-browser-quit-click.png), 但按钮
  未置灰、无 title 提示 —— 用户点了没任何反应。对照: 地址控件置灰+title 提示做得很完整。
- 建议: 与地址控件同款处理: 置灰 + title「仅桌面壳窗口可用」。

**P2-3 重启后终端历史清零无说明**
- 现象/建议: 新进程终端必然清空, 确认按钮或提示行加一句「重启后终端历史将清空」, 管理预期。

**P2-4 版式小刺**: 「最大客户端」label 换行为"最大客户/端"、"应用并重启"按钮文字换行为"应用并重/启"
  (01/02, 1440 逻辑宽即出现); 建议加宽列或改双字词 ("客户端上限"/"重启")。

### 惊喜点 (请保持)

- **等价命令实时刷新**: RangeValue 改 max-clients=3 的瞬间, 命令同步变 `--max-clients 3`; 📋 复制
  实测剪贴板逐字正确。
- **自我重启质量超出预期**: 原地两段确认 (按钮变「确认重启?」, 且数秒无操作自动回退防误触);
  断档实测 **≈0 秒** (旧地址失效与新地址就绪落在同一 100ms 轮询窗, 未观测到任何不可用间隙);
  新进程命令行实拍 `"…--addr 127.0.0.1:8090 --max-clients 4 --flow xonxoff --gui --port COM1
  --baud 115200 --config 8N2"` —— **--flow 跨重启携带 (ADR-10) 黑盒实锤**, 全配置无一丢失;
  新窗 equivCmd 即时指向新地址。
- **浏览器页的地址/重启控件处理得体**: 置灰 + title「以新地址重启桥 (仅桌面壳窗口可用, FR-9a)」,
  对浏览器用户讲清楚了"为什么点不了" (对比「退出程序」的处理, 见 P2-2)。
- **1013 拒连语义标准**: 脚本视角 code=1013 + reason "max clients" 逐字段可读; 被拒连接不计入
  clients、老客户端不受影响 (实测 clients 稳定)。
- **README 对照表 9/9 行逐项与 UI 实际位置一致** (走查 5): --port↔串口+扫描 (扫描后 COM1/2/8
  出现)、--baud↔波特率、--config↔数据位/校验/停止位、--max-clients↔最大客户端、--flow↔流控
  (位置对, 但见 P1-1/2)、--addr↔地址+应用并重启、--gui/--headless↔启动方式 (两形态均实测)、
  --no-open↔启动参数 (headless 实测 phase=closed 且 port=COM1 记忆)、--list-ports↔扫描按钮
  (CLI 实跑列出 COM1/COM2)。
- **--flow 数据面真实生效**: xonxoff 配置下 WS↔串口双向逐字节一致 (2784/2784、1920/1920、
  768/768 多轮)。环境注记: ELTIMA 虚拟对的驱动级 XON/XOFF 仿真会让对端一发 XOFF 全对暂停
  (写超时), 需两端重开才恢复 —— 端到端 XOFF 节流在本虚拟对无法干净验证, 建议真实硬件上由 QA
  补一轮; 此为环境限制非产品缺陷。
- **720 窄窗抽查通过**: 地址/应用并重启/最大客户端等全部新元素单列堆叠, 无破版无横向滚动
  (11-window-720.png)。
- **「退出程序」按钮进页面**: 桌面壳用户终于有了一键退出 (sprint 2 遗留诉求), 且浏览器侧被门控。

## 人工 30 秒清单

本轮全部自动化覆盖, 无必须人工项。可选复核:
1. 真实硬件 (USB-UART) 上验证 XOFF→桥发送暂停 / XON→恢复 (ELTIMA 仿真无法干净验证)。
2. 「确认重启?」自动回退的秒数是否合适 (实测 ~10s 内回退), 需要产品定一个数并 (可选) 告知用户。

10. 结论: 修掉 P1-1/2/3 (flow 三连 + 发送区卡死) 后, "同一件事两个入口做一遍"才真正成立。
