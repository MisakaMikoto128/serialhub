## 3. 新发现 NEW-1 (非工单): 终端合并/断行路径存在竞态 —— 建议记 P1, 交 Dev

FIX-1 的 20ms 合并窗口 + carry 机制在"**行未被 \n 终止**"(二进制流/无换行长流) 场景下出现确定性触发的渲染错误。**证据链排除桥/网络层**: CDP `framereceived` 抓帧显示浏览器网络层 100% 收到全部字节 (1B+89B / 1B+255B), `rxBytes` 同步全额入账; 无 `pageerror`、无 console error; headed 与 headless 行为完全一致 (排除后台定时器节流)。缺陷在页面渲染层 (ui/index.html)。三种形态:

| # | 输入 (清空后) | 期望 (按 FIX-1 设计) | 实测 |
|---|---|---|---|
| ① 重复渲染 | 90B(无\n) → 再 256B(无\n) | ≤346 字符 | **519~609 字符 (≈2×)**, 同内容出现两遍 |
| ② 断行丢失/乱序 | 256B 含内嵌 0x0A (无尾 \n) | 2 行 [10, 245] | 有时正确 [10,245], 有时 **[255] 单行 (0x0A 被渲染为 `·` 未断行)**; 有时行首多出 5 个 `·` (下一窗 carry 前置, 乱序) |
| ③ 乱序变体 | 同②, 空闲 2s 变体 | 同上 | 254 字符, 行首 21 点 = 尾部 5 点前置 + 头部 16 点 |

对照事实 (用于定界):
- 行以 \n 结尾的一切场景**从未出错**: FIX-1 的 10 行文本、FIX-4 复测 (尾部 \n) ×3、FIX-2 复测 —— 断行/合并/计数全对;
- 纯帧收集器 (pytest 套件, 无 DOM) 收同样字节流字节级无损 → 缺陷仅在 DOM 渲染路径;
- "无换行二进制 <512B 不显示"本身是**设计行为** (未完行 carry, 512B 强制断行, 与 Dev 报告一致, 实测 90B 无\n → 仅占位符, 正确); NEW-1 是 carry 挂起期间后续窗口到达时的 flush/重放竞态。

复现要点 (供 Dev): 桥 `--port COM1 --baud 115200 --config 8N2 --addr 127.0.0.1:8080`; COM2 灌数器 stdin 指令 `split1 <首段hex> <余段hex> <gapMs>` / `chunk <hex> <块> <gap> <次数>`; 操作 = 清空 → 灌数 → 读 `#term` innerText; 判定用页面内 `#lineCount` + innerText 逐字符比对。建议 Dev 用"多窗 carry + 无尾\n"用例单测 flush 状态机 (carry 只许消费一次 / flush 前后 buffer 清空幂等)。

影响评估: 文本行场景 (终端主流程, 行以 \n 结尾) 不受影响; 二进制协议流 (无换行) 会触发丢行/重复/乱序显示 —— 字节本身在桥侧无损 (rxBytes 精确), 仅显示层。**不阻塞本轮 FIX-1~6 验收, 但建议随下一个修复轮处理。**
