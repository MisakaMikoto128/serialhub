# 串口调试提效：把串口变成 WebSocket 字节管道，浏览器和脚本直接读写（开源工具 SerialHub 实战）

## 一、这些场景你大概率遇到过

写嵌入式固件的人，对下面三件事应该都不陌生：

- **串口被一个程序独占**。串口助手开着收数据，上位机脚本就打不开同一个 COM 口；想两边同时看，只能开一对虚拟串口，或者来回关开关开。
- **设备热拔插就要全部重连**。USB 线一碰、设备重新枚举，所有程序集体断线；更糟的是有的工具"窗口还开着、数据早就不来了"——你盯着空屏排查十分钟，其实是旧句柄在设备抖动后已经失效。
- **想在浏览器或脚本里摸串口**。无头浏览器里拿不到 Web Serial 授权，网页上位机根本连不上设备；自动化测试想用脚本假装一台设备跟被测系统对发字节，也缺一条顺手的管道。

SerialHub 就是为这些场景做的。它是一个 Apache-2.0 开源的**串口 ⇄ WebSocket 桥接管理器**：把串口设备变成一条 WebSocket 字节管道，浏览器页面和脚本直接读写原始字节。Rust 写的，跨平台单文件，网页管理台直接内嵌在二进制里，下载解压即用。

## 二、它是什么

一句话：**每块串口对应一座"桥"，桥的另一头是一个 WebSocket 数据网址；所有桥由一个固定的网页管理台统一管理。**

```
COM1 ══ 桥1 ══ ws://127.0.0.1:8101/ws ══ 网页上位机（自带协议栈）
COM3 ══ 桥2 ══ ws://127.0.0.1:8102/ws ══ Python 测试脚本
              │
     管理台 http://127.0.0.1:8080
     （建桥 / 启停 / 改配 / 删除 / 速率统计，重启自动恢复）
```

数据端口由程序自动分配（默认从 8101 起），桥的生命周期内不变。两个网址用一句话分清：**管理台网址管程序，数据网址管字节**——程序接入永远连数据网址。

做这个方向之前作者调研过一圈现成方案：有的在桥里做 Modbus、对外只吐 JSON；有的用 JSON+base64 包帧，页面侧协议栈得推倒重来；有的明确单客户端、没有广播；还有的已经停更好几年。SerialHub 的取舍是反过来的——**桥里不做任何协议语义，只搬运字节**。为什么这么选，第五部分细说。

## 三、快速上手

从 GitHub Releases 下载对应平台的压缩包解压即可（Windows x86_64 zip 约 1.6 MB / Linux x86_64 tar.gz 约 1.9 MB / macOS Apple Silicon tar.gz 约 1.9 MB），或在源码目录执行 `cargo install --path .`。

命令行三步（旧单桥参数 = 自动建一座桥并启动，命令与注释原样来自 README）：

```bash
# 列出本机串口
serialhub --list-ports

# 一行起桥: 串口 COM1, 115200, 8N2; 管理台地址 127.0.0.1:8080
serialhub --port COM1 --baud 115200 --config 8N2 --addr 127.0.0.1:8080
# 浏览器打开 http://127.0.0.1:8080 —— 管理台即用
# 程序接入: ws://127.0.0.1:8081/ws (本桥数据端点, 纯二进制; 裸地址 ws://127.0.0.1:8081 亦可)
```

它有两种形态：

- **桌面客户端**：Windows 双击 `serialhub.exe` 就是原生窗口 + 系统托盘，关窗退到后台，桥继续收发；
- **纯命令行**：脚本和 CI 场景加 `--headless`，无窗口无托盘：

```bash
serialhub --headless --port COM1   # 纯命令行模式 (脚本/CI)
```

串口参数是全覆盖的：波特率 110~2,000,000，数据位 7/8，校验 N/E/O，停止位 1/2，流控 none/rtscts/xonxoff。CLI 与管理台完全对等——界面上每个配置项在命令行都有对应物，管理台里还能一键复制与当前配置等价的启动命令。

## 五、关键实现思路

这一部分讲三个设计决策，素材来自仓库里的架构决策记录（ADR），想看原文的可以去仓库翻 decisions.md。

### 1. 数据面只做管道：纯原始二进制帧

串口桥最容易做偏的地方，是"顺手"帮你解析协议。调研里见过的反例就是 JSON+base64 包帧、桥内做 Modbus——桥一旦做语义，页面侧的协议栈就得跟着它的帧格式重写，接入那天就是推翻自家代码的一天。SerialHub 把定位钉死在"管道"：`/ws` 数据通道只传**原始二进制帧**，双向；组帧、解析、校验全部留给页面和脚本自己的协议栈。配置与状态走 `/api/*`（JSON），控制面与数据面彻底分离——管理台页面挂了不影响字节流动。

这个设计换来两条使用前必须心里有数的规则（手册「程序接入」章原文要点）：

- **WebSocket 消息边界 ≠ 串口帧边界**：设备一次 write 可能被拆成多条消息到达，多次 write 可能被合并成一条；请按你自己的协议组帧，不要依赖消息边界；
- **慢客户端丢旧帧**：下行缓冲 1024 条，消费跟不上时丢最旧帧保连接——不反压、不踢人。高波特率 + 慢消费端的组合，请确保消费端跟得上。

### 2. 多客户端：下行广播，上行 FIFO 单写者

串口本质是单用户设备，多个客户端同时写就是灾难。SerialHub 的仲裁很朴素：

- **下行（串口 → 客户端）用广播通道**：收到的字节推给所有客户端，测试脚本和网页可以同时围观同一条设备流；
- **上行（客户端 → 串口）单写者**：所有客户端的帧进一个 mpsc 队列，由唯一写者按 FIFO 顺序写入串口，先到先发——文档明示不做客户端优先级。

对比有的实现让每个会话各自轮询同一端口、互相抢字节，这条路至少保证了：不抢字节、不乱序、不 panic。

### 3. 自动重连：独立监督任务，重试全程可见

这个功能来自真实的教训：CH340 抖动一次，旧串口句柄可能永久失效，"桥活着却不转发"是极难排查的静默故障。所以 SerialHub 没有把重开写成 try-catch 兜底，而是做成一等公民：

- 一个**独立于数据面的监督任务**按 1 秒节奏重试，永不阻塞数据转发；
- 状态机 `Closed → Opening → Open → Retry` 全程在状态接口可见；
- 管理台明示「串口已断开，正在自动重连 (第 n 次)…」，第几次都数给你看。

对你的脚本来说什么都没发生：期间 WebSocket 客户端连接保持，设备插回来数秒内恢复，数据自动续传，客户端零动作。每座桥可以独立关掉这个开关（关了掉线就直接转「已停止」）。

顺带一组仓库更新日志里记录的自测基线（v1.0.0，仅供参考）：双向吞吐 7.3 / 10.4 Mbps，串口收到字节到 WebSocket 客户端收到的延迟 p95 约 0.61 ms。工程侧仓库里有 83 条 Rust 单元测试和 63 条跑在 COM1↔COM2 虚拟串口对上的集成测试，回归是有保障的。

## 六、客户端接入示例

### Python（摘自 examples/python-client.py，先 `pip install websockets`）

```python
DATA_URL = "ws://127.0.0.1:8090/ws"  # 改成你的桥数据网址


async def main():
    async with websockets.connect(DATA_URL) as ws:
        async def rx():  # 下行: 串口收到的原始字节, 打 HEX
            async for data in ws:
                print("收", data.hex(" "))

        async def tx():  # 上行: 每秒一行 "ping" (UTF-8 原始字节)
            while True:
                await asyncio.sleep(1)
                await ws.send(b"ping\n")

        await asyncio.gather(rx(), tx())
```

### 浏览器（摘自 examples/web-client.html，零依赖单文件，双击即用）

```js
ws = new WebSocket($('url').value);      // 数据端点: ws://<桥网址>/ws
ws.binaryType = 'arraybuffer';           // 铁律 1: 拿到的就是原始字节
ws.onmessage = e => log('收', new Uint8Array(e.data));   // 铁律 2: 只展示, 不组帧
```

发送侧：

```js
ws.send(new TextEncoder().encode(s));    // 二进制帧 → 桥串行写入串口
```

两个示例都在仓库 examples/ 目录，可直接跑。注意**管理台端口 ≠ 数据端口**，真实数据网址以桥卡片或启动输出为准。

## 七、限制与诚实声明

- **无 TLS、无鉴权（v1.x 现状）**：任何连得上管理台或数据网址的人都能读写字节、改配置。只在本机或可信内网使用，**勿暴露公网**；需要远程访问请自己套 SSH 隧道。
- **macOS 安装包未签名**：首次打开若被系统拦下，右键点文件选「打开」，再点一次「打开」即可放行。
- **Linux/macOS 桌面形态**需要 webkit2gtk / WKWebView 运行库；服务器脚本场景直接用 `--headless` 纯命令行。
- **Windows 发布版没有控制台黑窗**（双击即用），代价是 `--headless` 模式 stdout 不回显到终端——脚本判活请轮询 `/api/status`。
- **它不是串口终端仿真器**：不做 VT100/xterm 终端；管理台「串口数据」只能看不能发，发数据是客户端程序（网页/脚本）的职责。

# 调试嵌入式设备时，串口总被一个工具独占怎么办？我做了个开源的串口 ⇄ WebSocket 桥接管理器

做嵌入式联调的人都知道，串口是个独木桥：物理上只有一个口，软件上还是独占打开——一个程序占着，别的程序就只剩干瞪眼。

最近联调一块工控板，我同时需要三个角色：一个网页上位机发指令看回包，一个 pytest 脚本假装从站收发报文，偶尔还想开串口助手扫一眼原始流。以前的解法是开一对虚拟串口把三个角色串起来，结果有一次 USB 线被人碰了一下，设备重新枚举，三个程序集体断线，全部从头再来。更坑的是有些工具断线之后"窗口还开着、数据早就不来了"，你盯着空屏排查半天，最后发现是拔插的锅。

那次之后我把这套流程整个换掉了，换成了自己做的开源工具 SerialHub——用 Rust 写的串口 ⇄ WebSocket 桥接管理器，Apache-2.0 协议，Windows / Linux / macOS 都是单文件免安装。它干的事一句话说得清：**把串口变成一条 WebSocket 字节管道，浏览器页面和脚本直接读写原始字节**。

上手小到不像个"工具"，就一行命令：

```bash
serialhub --port COM1 --baud 115200 --config 8N2 --addr 127.0.0.1:8080
```

浏览器打开 `http://127.0.0.1:8080` 就是管理台。当然也可以双击桌面图标——它默认就是个带系统托盘的桌面应用，关窗退到后台，桥照常收发；想跑在服务器上喂脚本，加个 `--headless` 就是纯命令行。

用了这段时间，真正让我留下来的是三件事。

**第一件，多桥管理台。** 所有桥在一个网页里管理：建桥、启停、改配置、删除，每行一座桥，状态徽章、连接数、最近错误一眼看完。收发速率是每秒跳动的火花线，配一张「串口 ⇄ 桥 ⇄ 数据网址」的流程图，有数据流动线路就点亮——串口有没有在干活，瞄一眼就知道。桥的配置会自动落盘，程序重启后全部桥原样恢复，不用每天早上重新建一遍。

![管理台总览](docs/images/dashboard.png)

**第二件，热拔插自动重连。** 这是最戳我的。现在拔掉设备，管理台上明明白白写着「串口已断开，正在自动重连 (第 n 次)…」，第几次都数给你看；插回去，数秒内恢复，弹一条「串口已恢复」的横幅，不打断任何操作。最舒服的是脚本侧全程无感：WebSocket 连接一直保持着，恢复后数据自动续传，pytest 脚本一行都不用改。以前那种"设备一抖、全体重来"的日子，就这么没了。

![速率与流程图](docs/images/flow-stats.png)

**第三件，它只做管道，不做协议。** 桥的数据通道里跑的是纯原始二进制帧，组帧、解析、校验全部留给页面和脚本自己的协议栈。刚开始我还有点不适应——组帧不是挺常见的功能吗？后来想明白了：页面侧本来就自带协议栈，桥一旦"好心"帮你包帧（JSON、base64 之类），接入那天就是推翻自家协议栈的一天。管道什么都不做，反而谁都能接。想看原始流的时候，点开桥的抽屉有「串口数据」页签，只读旁看，ASCII 和 HEX 随时切。

![只读旁看串口原始流](docs/images/bridge-drawer.png)

还有一些顺手的小设计：多客户端连同一座桥时，串口收到的字节广播给所有人，围观同一条设备流很方便，上行自动排队也不会互相踩踏；管理台内置四套主题，其中有一套 Windows 95，青灰配色加直角立体按钮，怀旧感直接拉满；最近几个版本还把窗口大小位置记忆、新建桥表单记住上次参数这些细节补齐了，能感觉到迭代很勤。

当然也得把短板说清楚，免得你踩坑：

- **没有 TLS、没有鉴权**（当前版本现状）：连得上网址就能读写字节，所以只在本机或可信内网用，千万别暴露公网；
- **macOS 安装包未签名**：首次打开被系统拦下时，右键选「打开」再确认一次即可；
- 它**不是串口终端**：管理台里只能看不能发，发数据是客户端程序（网页/脚本）的职责。

如果你也受够了"一个串口，全家排队"，可以试试。官网有下载和三步上手，仓库里有源码、手册，还有两个可直接跑的接入示例（网页和 Python 各一个）：

- 官网：https://misakamikoto128.github.io/serialhub/
- GitHub：https://github.com/MisakaMikoto128/serialhub

觉得有用的话，去仓库点个 star 就是最好的支持；有不顺手的地方也欢迎提 issue。

### 2. 两篇差异说明 (避免一稿多发判定)

两篇共用同一套**事实**，但**文本、结构、开头、标题、配图、代码量全部不同**，无成段重复：

| 维度 | CSDN 版 | 知乎版 |
|---|---|---|
| 调性 | 技术干货（实现思路占大头） | 经验分享（第一人称叙事，场景切入） |
| 开头 | 三条痛点清单式归纳 | 一次联调断线的具体场景故事 |
| 结构 | 痛点 → 是什么 → 上手 → 管理台 → 实现思路 ×3 → 接入示例 → 限制 → 链接 | 场景 → 是什么 → 三件留下来的事 → 小设计 → 短板 → 链接 |
| 代码 | 4 段（CLI、Python、JS×2） | 1 段（1 行 CLI） |
| 配图 | 5 张（含 CLI 形态） | 3 张（纯管理台体验） |
| 标题 | 关键词前置（串口调试/WebSocket/嵌入式） | 问题式/经验式，不带关键词堆砌 |

建议两篇错开发布时间（如同一天上午/下午，或隔天），进一步降低同源判定风险。
